Reliable Daily Ingestion on Vercel

A minimal production architecture for ingesting seven salvage-yard providers, reconciling a canonical Turso inventory, projecting it into Algolia, and delivering saved-search alerts. Three independent reviews covering Vercel execution, Turso correctness, and end-to-end ETL semantics accepted this design with no unresolved critical or high-severity blocker.

Decision

Keep the existing platform:

  • Vercel Cron and Vercel Workflow for scheduling and durable orchestration
  • Turso as the system of record
  • Algolia as the public search index
  • Existing email and Discord providers for alerts

No Kafka, Vercel Queues, mandatory Blob artifacts, Railway worker, Postgres migration, or immutable inventory-generation system is required.

Architecture

Hourly Vercel Cron
  -> database due-check
  -> global Workflow executor hook
  -> create or resume singleton ingestion run
  -> process sources sequentially
      -> fetch bounded chunk
      -> guarded atomic Turso batch
      -> advance source cursor
  -> validate and accept/reject each source
  -> bounded upsert reconciliation
  -> bounded missing reconciliation
  -> mark inventory published/degraded
  -> bounded ordered Algolia projection
  -> mark search published
  -> bounded alert matching and durable intent creation
  -> release ingestion singleton
  -> non-blocking notification delivery and cleanup

Execution and recovery

Scheduling

Cron is a wakeup, not the source of truth. It runs hourly. Turso atomically decides whether today is due, an active run should be resumed, or the call should no-op. The ingestion run ID is independent from the Workflow run ID.

Singleton execution

A database constraint permits exactly one nonterminal ingestion run. A fixed Workflow hook prevents multiple active executors. Database cursor guards remain the correctness boundary if two executors overlap.

Resumption

There is no age-based lock takeover. A failed Workflow leaves its durable run state intact. A later hourly invocation starts a new Workflow that resumes the stored source or reconciliation cursor.

Abandonment

Normal abandonment is allowed only before reconciliation begins. Emergency abandonment after live reconciliation starts sets full_reindex_required. The next successful run must rebuild the complete Algolia index before clearing the flag and releasing the singleton. The repair publication is explicitly alert-degraded.

Source ingestion

Sources run sequentially initially. Every step fetches one measured chunk, then performs one backend write batch:

  1. Guard snapshot insertion on the expected run, source state, and cursor.
  2. Guard cursor and counter advancement with the identical predicate.
  3. Execute both operations with client.batch(statements, "write").
  4. Treat rowsAffected === 1 as the winning transition.
  5. Treat rowsAffected === 0 as a stale retry and return the stored checkpoint.

A transaction error rolls back every statement. A lost response can safely retry. Chunk size is chosen by measured records, bytes, Turso commit latency, Workflow duration, and total Workflow event budget.

Validation

A source is accepted only after checking terminal cursor evidence, actual unique snapshot rows, source-specific minimum inventory, recent-run drift, duplicate rates, and rejected-record rates. A rejected partial snapshot never reaches reconciliation.

Rejected-source rule: a rejected source contributes no new rows. Existing vehicles owned by it do not advance missing state. An accepted source reporting the same VIN may still replace ownership according to the documented source priority.

Bounded reconciliation

The ingestion run persists a reconciliation phase, VIN cursor, and last-progress timestamp.

Phase Behavior
upsert Keyset-query the next canonical-winner page from accepted source snapshots, update vehicles, insert deduplicated changes, and advance the cursor in one guarded batch.
missing Keyset-query existing vehicles, apply missing or delete transitions only for eligible accepted sources, insert deduplicated changes, and advance the cursor.
complete Persist final counts and the published or published-degraded inventory outcome.

The live Turso table may be partially updated during reconciliation. This is an explicit consistency choice. Algolia continues serving the previous public inventory, and homepage statistics use stored counts from the last published run instead of a live table count.

Algolia publication

The projector handles one ordered change batch per Workflow step. Every Algolia task is awaited before its Turso checkpoint advances. VIN remains the idempotent Algolia object ID. Changes are read only from fully reconciled runs, and no newer ingestion starts until the current search publication completes.

A periodic or manual full-index replacement is the drift-repair path and is mandatory after forced abandonment during reconciliation or projection.

Alerts and consent

Saved-search matching runs in bounded steps against the stable newly published index before a newer ingestion may begin. Matching persists deterministic notification intents. Delivery occurs afterward and does not block future ingestion.

  • search_match_version changes when the query or filters change.
  • Email and Discord have independent configuration versions and channel start sequences.
  • Changing one channel cannot cancel valid intents for the other.
  • Disabling a channel atomically cancels only that channel's undelivered intents.
  • Delivery rechecks search existence, matching version, channel version, current consent, subscription, and channel eligibility.
  • Oversized searches are durably quarantined with an actionable reason. Their alert window advances so one search cannot wedge the pipeline, and a later complete scan clears the quarantine.

Email delivery uses provider idempotency keys. Discord uses a stable enforced nonce, but Discord only retains nonce uniqueness briefly, so a crash followed by a delayed retry can still create a rare duplicate.

Monitoring

Health derives from stored state, not a heartbeat request:

  • Age of the last successful search publication
  • Current ingestion stage and last-progress age
  • Published-degraded source details
  • Algolia projector lag
  • Alert matching and delivery degradation

Inventory, search, and alert health are reported separately.

Implementation sequence

  1. Stop the current failure: expose the raw libSQL client, replace interactive checkpoint transactions with guarded backend batches, and run sources sequentially.
  2. Add durable run control: hourly due-check, atomic singleton run, resumable Workflow identity, explicit stages, and freshness monitoring.
  3. Bound downstream work: resumable reconciliation, ordered bounded Algolia projection, and bounded cleanup.
  4. Harden source acceptance: unique-row counts, minimums, drift limits, duplicate ratios, and source-specific terminal evidence.
  5. Harden alerts: publication sequence, bounded matching, durable intents, per-channel versions, cancellation, and delivery revalidation.
  6. Add disaster recovery: forced-abandon semantics and complete Algolia rebuild.

Implementation status

All six implementation phases are present in the repository. The delivered changes include the additive Turso migration, hourly recovery scheduling, guarded source checkpoints, source acceptance, bounded reconciliation, incremental and full-repair Algolia projection, durable per-channel notification intents, bounded delivery, abandonment controls, and pipeline observability.

Local verification: 219 tests pass with 639 assertions. Type checking, linting, the production Next.js and Workflow build, SQL migration execution, and whitespace validation also pass.

The migration has not been applied to the production Turso database and the code has not been deployed. Those are deliberately separate rollout actions. The production measurements and live failure-injection checks below still gate enabling the new schedule.

Production acceptance gates

The design is accepted, but production rollout remains gated by measurement.
  • Raw Turso write-batch p99 below one second
  • Zero ingestion-caused application write failures
  • Normal application writes remain inside an explicit latency SLO
  • Workflow step p99 below 120 seconds
  • Peak function memory below 70 percent
  • Normal run below 500 steps and 2,000 Workflow events
  • Complete sequential run below 12 hours
  • Successful run at twice current inventory volume under normal application traffic

Failure-injection suite

  • Terminate immediately after a Turso commit, before Workflow records success.
  • Race two executions using the same requested cursor.
  • Lose the HTTP response after a committed batch.
  • Crash after every reconciliation and projection batch boundary.
  • Return clean-empty, truncated, duplicate-heavy, and rejection-heavy provider results.
  • Simulate Turso, Algolia, provider, email, and Discord outages.
  • Miss one Cron invocation and duplicate another.
  • Deploy additive schema changes during an active pinned Workflow.
  • Force abandonment during reconciliation and confirm mandatory full-index repair.
  • Change alert consent after matching but before delivery.

Escalation criteria

If no source chunk size satisfies both the Turso commit-latency gate and the Vercel Workflow event budget, introduce intra-chunk staging with an attempt ID and batch ordinal. If short, guarded batches still cause application write failures or unacceptable latency, then reconsider Postgres or a dedicated worker runtime.
